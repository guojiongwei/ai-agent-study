# 代码审查

## 审查清单

### 1. 正确性

- 逻辑是否满足需求；边界情况（空值、空数组、0、负数、超长输入）是否处理
- 异步调用是否遗漏 `await`；异常是否被吞掉
- 是否存在循环依赖、共享可变状态导致的意外副作用

### 2. 可读性

- 命名是否表意（变量/函数用 camelCase，类型用 PascalCase）
- 函数是否过长、嵌套是否过深
- 注释是否解释"为什么"，而不是重复"做了什么"

### 3. 健壮性

- 外部输入（用户输入、接口返回、文件内容）是否校验
- 失败路径是否明确处理，错误信息是否可读（中文）
- 是否存在静默失败（`catch` 之后什么都不做）

### 4. 性能与安全

- 是否有不必要的重复计算、重复请求
- 循环内是否存在本可避免的 I/O 操作
- 是否把密钥、令牌等敏感信息硬编码进代码

## 输出格式

按严重程度分组，每条给出「位置 + 问题 + 建议」：

- 【必须修复】会导致功能错误、数据损坏或安全问题
- 【建议修改】影响可维护性、可读性
- 【可选优化】风格与个人偏好

示例：

> 【必须修复】`src/utils.ts#L42` —— `pendingTool` 可能为 `null` 却直接取 `.args`，会抛 `TypeError`。建议先用 `if (pendingTool)` 判空。

## 原则

- 只针对本次改动的代码提意见，不扩大到无关代码
- 不确定的地方先说明假设，不要臆断
- 确实没问题就直接说明，不要为凑数而挑毛病
